# ADR-0004: Phone-OTP-first authentication on Supabase Auth

**Status:** Proposed · **Date:** 2026-09-27

## Context
In Ghana the phone number is the identity; many users rarely use email. SPEC §20: phone + OTP primary, email/password where appropriate, Google/Apple later, no plaintext passwords. SMS costs money and OTP endpoints attract abuse.

## Decision
- **Supabase Auth** phone OTP for all users. SMS is delivered via Supabase's **Send SMS Hook**, which calls `/api/internal/auth/send-sms` (hook secret verified) and then our `SmsProvider` interface. That lets us use a Ghana-local SMS vendor even if Supabase has no built-in integration for it.
- **Email + password** optional (mainly providers on desktop). Supabase hashes passwords.
- **Guests** = OTP-verified phone, no password/profile setup required (pending product-owner confirmation).
- **Google/Apple** via Supabase OAuth later; no schema change needed.
- Web sessions via `@supabase/ssr` httpOnly cookies. Mobile uses Bearer access tokens with refresh rotation.
- Local/dev: `MockSmsProvider` + Supabase test OTPs. No SMS spend outside production.
- Abuse controls: Supabase rate limits, a per-phone hourly cap in our hook, short OTP expiry, Turnstile if needed.

## Alternatives
| Option | Pros | Cons |
|---|---|---|
| Supabase built-in SMS providers (e.g. Twilio) | No hook code | International SMS to Ghana costs more and delivery is less predictable; vendor fixed by Supabase's list |
| Clerk / Auth0 | Polished UI | Another vendor; JWT bridging to RLS; cost per MAU |
| WhatsApp OTP | Cheaper, popular | Needs WhatsApp Business Platform approval + templates; add later as a channel inside the same hook |
| Magic links (email) | No SMS cost | Doesn't fit how Ghanaian users sign in |

## Consequences
- We own the SMS hook's reliability (retries, fallback vendor later).
- One identity per phone number. Changing phone requires OTP on the new number.
